# E4.1 — Implement BullMQ Scan Job Queue

**Status:** done  
**Date:** 2026-08-12  
**Epic:** E4 — Repository Scanner & Job Orchestration  

---

## User Story

As the **Platform**, I want scan jobs in a durable queue, so that long analyses don't block API requests.

---

## Acceptance Criteria

- **AC1:** Given scan request, when enqueued via `POST /queue/scan`, then job status `queued` returned within 30 seconds.
- **AC2:** Given worker crash mid-job, when retry policy applies, then job retried up to 3 times with exponential backoff.

---

## Technical Tasks

- [x] **Task 1:** Enhance `QueueService` (`apps/api/src/queue/queue.service.ts`) with `enqueueScanJob(payload)` enforcing 3 retries with exponential backoff and `getScanJobStatus(jobId)` for job status retrieval.
- [x] **Task 2:** Create `QueueController` (`apps/api/src/queue/queue.controller.ts`) with `POST /queue/scan` and `GET /queue/scan/:jobId` endpoints protected by `ClerkAuthGuard` and `RolesGuard`.
- [x] **Task 3:** Register `QueueController` in `QueueModule` (`apps/api/src/queue/queue.module.ts`).
- [x] **Task 4:** Add unit tests in `queue.service.test.ts` and `queue.controller.test.ts` verifying AC1 & AC2.

## Dev Agent Record

### Implementation Plan
1. Extended `QueueService` to support durable scan job enqueueing with BullMQ retry policy (`attempts: 3`, `backoff: { type: 'exponential', delay: 1000 }`).
2. Created `QueueController` providing:
   - `POST /queue/scan`: Returns HTTP `202 Accepted` payload with `{ job_id, scan_id, repository_id, status: 'queued', attempts_max: 3 }`.
   - `GET /queue/scan/:jobId`: Returns current job status, attempt count, and retry state.
3. Updated `QueueModule` registering `QueueController`.
4. Added unit tests for service and controller.
